# Actors Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let a site owner schedule device actions from a Schedule tab, run by a new `actron-neo-actor` container that switches a ducted Actron Neo air conditioner off during tariff demand windows and restores it.

**Architecture:** Core API stores actor instances, schedules and runs, serves an actor-facing API (key-authenticated, like collectors) and an owner-facing API (JWT). The actor is its own container: it declares its capabilities, keeps a synced copy of the unit's state, decides what is due, acts, and reports. The web app draws the schedule form from the declared capabilities.

**Tech Stack:** Core API: Python 3.12, FastAPI, SQLAlchemy 2, Alembic, APScheduler, pytest. Actor: Python 3.12, httpx, `actron-neo-api` 0.5.16, respx, pytest. Web app: React 19, TypeScript, TanStack Query, Tailwind, vitest.

**Spec:** `docs/superpowers/specs/2026-11-04-actors-design.md`. Mockup: `docs/superpowers/specs/2026-11-04-actors-schedule-mockup.html`. Read both before starting.

## Global Constraints

- Work on branch `feat/actors` (use superpowers:using-git-worktrees). Commit messages end with `Co-Authored-By: Claude Sonnet 5.5 <noreply@anthropic.com>`.
- CLAUDE.md: functions at most 30 lines, no `any` in TypeScript, group more than 3 props into an object, handle errors on every async call, no secret in plaintext (refresh tokens go in `ActorInstance.config`, an `EncryptedJSON` column), never log or store secrets. Run `/simplify` before the final hand-off.
- Prose (comments, docs, commit messages) follows `.claude/rules/avoid-ai-writing.md`.
- Ruff line length 120; actor package needs Python `>=3.12` (the library requires it).
- Actor auth: env `ACTOR_KEY` in core-api and the actor; headers `X-Actor-Key` and `X-Actor-Provider` (`actron_neo`); one key for all actors; every actor endpoint checks the instance's provider.
- Run outcomes: `pending`, `running`, `ok`, `skipped`, `failed`, `overridden`. Run kinds: `action`, `restore`, `test`. Unique (`schedule_id`, `kind`, `trigger_at`).
- Timings: missed-trigger grace 10 minutes; a reading older than 5 minutes is stale; confirm a command by checking synced state for 45 seconds; push fallback polls every 30 seconds; reconcile poll every 5 minutes; heartbeat to Core API every minute; push reconnect backoff caps at 5 minutes; watchdog job every minute and treats the actor as silent after 5 minutes; failures tile refreshes about every 15 seconds.
- Device facts (verified on the owner's unit): `set_system_mode("COOL")` turns on and `set_system_mode("OFF")` turns off, each visible in `is_on` after about 6 seconds, and `mode` stays `COOL` while off; `remote_zone_info[i].enable(bool)` works the same; indoor temperature is `master_info.live_temp_c`, outdoor is `master_info.live_outdoor_temp_c` (not `ac_system.outdoor_unit.amb_temp`, which reads 0.0); the raw status holds the wall controller PIN and installer contact details, so the actor never logs or stores it.
- Site roles: only the owner (`require_site_owner`) writes; viewers (`require_site_access`) read.

## Review Focus

Each line has its test in the named task.

1. A demand window that crosses midnight, or sits across a DST change, gives correct start and end instants (Task 4).
2. The actor restarts while it holds the unit off: it finds the unfinished run and restores at the right time; a second create of the same trigger returns 409 and is not run twice (Tasks 6, 13).
3. A schedule, instance or site is disabled while the unit is off: discovery keeps the instance as `restore_only` until the restore finishes (Tasks 5, 13).
4. A stale or missing reading skips an action's "only if" check but never blocks a restore (Task 10).
5. The unit is already off at the window start, or the owner switches it on mid-window: no restore of the owner's settings, outcome `overridden` or `skipped` as the spec says (Tasks 11, 13).
6. The raw device status, with the PIN, never reaches Core API or a log line (Task 11).

### Task 11: Device layer (state sync and commands)

**Files:**
- Create: `actron-neo-actor/actron_neo_actor/device.py`, `actron-neo-actor/actron_neo_actor/capabilities.py`, `actron-neo-actor/tests/test_device.py`, `actron-neo-actor/tests/fakes.py`

  - `class Device(Protocol)`: `state() -> DeviceState | None`; `capabilities() -> dict`; `snapshot_for(action_id, params) -> dict`; `apply(action_id, params) -> None` (raises `DeviceError`); `restore(snapshot: dict, current: DeviceState) -> RestoreResult` (lists fields restored and fields skipped because the owner changed them); `matches_action(action_id, params, state) -> bool`; `async start_sync()`/`stop_sync()`.
  - `ActronDevice(api: ActronAirAPI, serial: str, settings: Settings)` implements it. `capabilities.py` builds the declaration: actions `system_off`, `system_on` (mode choice from `mode_support`), `set_mode`, `set_temperature`, `set_fan_mode`, `set_zones` (multi_choice zones from `title`, plus `enabled` bool), readings `indoor_temp_c`, `outdoor_temp_c`, `humidity_pct`, `zone_temp_c` (targets = zone titles), `is_on`.
  - Sync: `start_push([serial])` with `subscribe_system_updates`; if it returns `False` or the connection drops, poll `update_status()` every `poll_fallback_seconds` and retry push with growing delay up to 300 seconds; reconcile poll every `reconcile_seconds`.
